- 原消息文本、图片字节及顺序在 Responses 转换后保持一致。

## 现有 API 的实测

只发起了 5 次工程探测，均使用 GPT-6.1-sol / high，发送 temperature 0、seed 137、max_output_tokens 8,192。

| 探测 | 请求数 | 成功 | 结果未知的传输断开 | 时间 |
| --- | ---: | ---: | ---: | --- |
| 单个文本请求 | 1 | 1 | 0 | 81.50 秒，返回 OK |
| 同时发出四个两图请求 | 4 | 1 | 3 | 窗口 179.78 秒；成功请求 81.64 秒 |

成功图片请求正确返回第一张红色、第二张蓝色。三个断开分别约 132.27、150.90、179.77 秒。这个样本不能确定稳定 QPS；没有对失败请求重试。新增 API 尚无凭据可供实测，配置示例支持分别验证和独立限速。

两个成功回包都报告模型 GPT-6.1-sol、reasoning effort high，同时报告 temperature 1、max_output_tokens null、未报告 seed，并包含客户端没有发送的系统 instructions。回报字段不能证明服务内部实际执行了哪些参数。原生请求和响应在工程诊断目录保留，安全摘要见 `diagnostics/api-behavior-audit.json`。

正式启动需要处理这个已观察到的差异：接受并记录这些上游差异，或使用能严格透传既定参数的 API。当前 `validated=false`，正式模型请求为 0；这一决定来自用户“只改 API，其他一律不改”的要求。

## 等待、并发和结果

HTTP 等待 36,000 秒（10 小时），API 排队 604,800 秒（7 天），单题臂进程 864,000 秒（10 天）；原程序执行上限保持 30 秒。中转站提前断开仍会记录为结果未知。

现有 API 初始在途上限为 1，两臂进程数为 2。`config.example.json` 中两项 API 具有相同的每 API 在途、限速和超时设置。新增 API 可提高总在途数；同题两臂及各轮固定使用同一 API。

正式结果在服务器独立目录生成，`GPTexp.deploy collect` 回收到 Mac 的 `GPTexp/runs/<run-id>`。统一输出包含 `results_and_full_trajectories.json`、`experiment_trace.jsonl`、`comparison.json` 和 `report.md`。已发出但结果未知的请求保留，不自动重答、切换 API 或修改固定分母。

导出逐题保留完整轨迹，统计阶段在内存中保留答案与状态字段。请求统计分别记录获准发送的尝试、收到的响应、结果未知的传输断开和排队意向；未获准发送的意向不计作发送尝试。

评分后生成 `scored_pairs.json`，可按题对核对参考答案、两臂预测、状态、正确性和 API 身份。汇总同时报告两臂各自独有的正确题数与准确率差。回收包含预算账本和暂停回执，排除文件锁及原始宿主参考索引。
